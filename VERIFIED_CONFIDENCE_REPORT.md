**Root cause — verified, and it is a packaging bug, not just a test bug:**
- `tsconfig.json:26` → `"importHelpers": true`, so TypeScript emits `require("tslib")` for downlevel helpers.
- `grep -c tslib package.json` → **0**. `tslib` is in neither `dependencies` nor `devDependencies`.
- `ls node_modules/tslib` → **not installed**.

Because `importHelpers` is a compiler-wide setting, **any** emitted module needing a helper will `require('tslib')` at runtime. This is not confined to the test environment: a consumer who `npm install`s the published package gets no `tslib` and can hit `Cannot find module 'tslib'` in production. The published tarball ships `lib/`, which is built by `tsup` — the bundler may inline helpers for some entry points, which would mask the problem intermittently rather than remove it.

**Severity: major** — a published MIT package with an undeclared runtime dependency; also the sole reason 0 encryption tests execute in the repo's own CI.
**Effort: S** — add `"tslib": "^2.x"` to `dependencies` (it belongs in `dependencies`, not `devDependencies`, precisely because `importHelpers` makes it a runtime requirement), or set `"importHelpers": false`.
**Not fixed** — outside the permitted fix scope (Step 0 / Step 0B only).

### 5.3 🟡 Type-check / `npm run build` fails on test-file-only errors

```
$ npx tsc --noEmit
src/core/BaseAdapter.test.ts(223,17): error TS2341: Property 'isRetryableError' is private and only accessible within class 'BaseAdapter'.
src/core/BaseAdapter.test.ts(227,17): error TS2341: Property 'isRetryableError' is private and only accessible within class 'BaseAdapter'.
src/core/BaseAdapter.test.ts(231,17): error TS2341: Property 'isRetryableError' is private and only accessible within class 'BaseAdapter'.
src/core/BaseAdapter.test.ts(240,17): error TS2341: Property 'isRetryableError' is private and only accessible within class 'BaseAdapter'.
src/core/BaseAdapter.test.ts(244,17): error TS2341: Property 'isRetryableError' is private and only accessible within class 'BaseAdapter'.
```

All 5 errors are the same pattern: the test reaches into `BaseAdapter`'s private `isRetryableError`. `ts-jest` permits this at test runtime (hence 319/319 passing), but `tsc` does not.

**Consequence:** `npm run build` — which runs `rimraf lib && tsc --module ESNext && tsc --module CommonJS` — **fails at the first `tsc`, after `lib/` has already been deleted.** A developer running `npm run build` ends up with a wiped/partial `lib/`. The publishable path is safe: `prepublishOnly` runs `build:dist` (tsup), which **succeeds (exit 0)** and produces `lib/index.js` (142.66 KB), `lib/index.d.ts` and `lib/index.d.mts` (112.74 KB each).

**Severity: minor** (build script hygiene; publishing is unaffected). **Effort: S** — exclude `**/*.test.ts` from the build tsconfig, or access the private member via a bracket/`as any` seam in the test.

### 5.4 🟡 `package.json` export-condition ordering warning

`tsup` emits:
```
The "require" condition comes earlier and will be used for all "require" calls:
    package.json:11:6:  "require": "./lib/index.js",
  ...over
    package.json:10:6:  "import": "./lib/index.mjs",
```
In `exports["."]`, `"import"` is listed before `"require"`, but `"types"` is listed last. Convention is `types` → `import` → `require`. Also, `"module": "./lib/index.mjs"` and `exports["."].import` point at `lib/index.mjs`, while `build:dist` was observed emitting `lib/index.js` (CJS) plus `.d.ts`/`.d.mts` — worth confirming the ESM artifact is actually produced under the name the manifest advertises before the next publish.
**Severity: minor** (potential dual-package resolution problem for ESM consumers). **Effort: S** — reorder conditions and verify the emitted filenames against the manifest.
